## Classification conventions

- **PHYSICS** - computes unit rates/sizes/balances from drivers and writes them on the graph. In v2 these are pure solve functions.
- **RENDER** - renders documents/pages/registers/exports from the graph and other documents, writing no graph state. Engineering calcs inside a renderer become pure functions the renderer calls. In v2: pure renderers.
- **BOOKKEEPING** - writes provenance/bookkeeping artifacts only (receipt/staleness/registry/normalization machinery). In v2 these die.
- **MIXED** - physics coupled to write-back (graph topology mutation, doc-in-doc appends, placement-file writes, task-board gates). Each is split: the solve half migrates as a function, the write-back half becomes a builder/composer or dies.
- Flags per stage: `writes_graph` (in the successive-substitution loop), `quick` (runs under regen --quick), `group=cad` (only with --cad).

## Migration risk summary (five largest)

1. **The placement seed is a hidden bus.** 15 stages read `flow_graph/placement_seed.json`, one graph-phase stage (`ree_recover`) writes it back, two doc stages amend datums - none declares `placement_refine`. In v2 the placement model must be a first-class solve input with declared edges, or 15 renderers silently depend on an undeclared ordering.
2. **Doc-on-doc write-back couplings.** `code_basis` appends into 10 documents after their writers run; `doc_test_rigs`/`parametric_model_report` append into `sizing/EW_CELLS.md`; `pid_sheets` rewrites `DRAWING_REGISTER.md` (undeclared); `doc_ga_check`+`doc_cad_clash` share a staged `.tmp`+`os.replace` handshake; `doc_sif` amends `hazop_actions.csv`. v2 must make these compositions (one renderer, many sections) instead of appends into neighbours' files.
3. **Physics/render split inside single scripts.** 32 MIXED stages each contain a calc and a write-back (graph stamp, doc, sidecar) in one process; the 2026-10-19 balance-vs-writers disagreement (single-writer rule R10a) is exactly this class of bug. The split must be mechanical: pure solve functions returning values, renderers consuming the solved graph, one writer per field.
4. **Order-by-array-position.** 25 stages with empty `depends_on` are sequenced only by manifest position, and `load_list`/`one_line` correctness depends on running after the LAST graph write. v2 must derive order from dataflow, or every one of these becomes a latent staleness bug.
5. **Provenance bookkeeping is load-bearing today, dead weight in v2.** The `_generated.json` pattern manifests, per-file manifests, receipt vouches and `_rev_stamp` gates exist because stage outputs cannot be re-derived cheaply; the 2026-11-03 oscilflapse (one oscillating SVG un-vouched 476 patterns / 959 files) shows the blast radius. The v2 solve-hash model must land BEFORE these are deleted, and the doc-phase convergence rule (render-until-stable) must survive the flake fixes that live inside `render_layer_views`.
